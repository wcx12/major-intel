# school_lookup 能力边界审计（2026-06-02）

## 审计目标

这次不是验证 `_test.py` 是否通过，而是用真实 MySQL 数据跑 `school_lookup`，再逐条人工判断：

- `ok` 是否真的可以安全交给上层 agent 使用。
- `needs_clarification` 是否覆盖了真实歧义。
- `not_found` 是合理保守，还是别名/抽槽能力缺口。
- fallback 的 `short/old_name/name LIKE` 是否造成过度自信。

审计脚本：`tmp/school_lookup_boundary_audit.py`  
样本数：50 条，覆盖精确名、代码、确认别名、高危简称、歧义简称、宽泛词、自然语言上下文和负样本。

## 总体结论

`school_lookup` 还不能算完备。

它在“全称/代码/已确认唯一别名”上表现稳定；在已 seed 的歧义简称上也能正确返回 `needs_clarification`。但它的 fallback 仍然危险：只要输入是短词、宽泛词或未 seed 简称，就可能从 `LIKE` 结果里直接选第一条并返回 `ok`。这会把“候选检索”误包装成“实体解析成功”。

## 根因判断

当前 `school_lookup` 有两条能力线：

1. `entity_aliases`：质量较高。唯一别名直接 `ok`，多别名返回 `needs_clarification`。
2. fallback SQL：风险较高。它把 `short LIKE`、`old_name LIKE`、`name LIKE` 的第一条结果也包装为 `ok`。

危险项几乎都来自第二条线。问题不是“搜不到”，而是“搜到了很多，但不该替用户选第一个”。

## 建议的验收规则

后续判断这个工具是否完备，不应该只看命中率，而应该先守住安全性：

1. 全称、代码、内部 id、唯一确认别名可以返回 `ok`。
2. 多个确认别名必须返回 `needs_clarification`。
3. 短词、单字、类别词、宽泛后缀词命中 fallback 时，不应返回 `ok`。
4. fallback 如果候选超过 1 个，默认应返回 `needs_clarification` 或 `partial_candidates` 类状态；至少不能填 `normalized_slots.school_name`。
5. raw 自然语言句子不应直接送进 `school_lookup`；自然语言入口需要先抽出学校槽位。

## 推荐下一步

优先级从高到低：

1. 给 fallback 加“安全阈值”：短词、单字、宽泛词、多候选时不直接 `ok`。
2. 把 `华大`、`南理`、`科技大学`、`师范大学`、`医科大学`、`电子`、`交通`、`大学`、`大` 固化为危险样本。
3. 补 `重邮`、`北工大`、`河大`、`哈工/哈工大` 的 alias seed。
4. 对自然语言入口单独审计：确认它会把“孩子想去杭电”抽成 `school_text=杭电`，而不是原句传入。
5. 最后再把本报告里的人工判定转成 golden dataset 或 `_test.py` 回归测试。
