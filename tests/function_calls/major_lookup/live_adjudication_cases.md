# major_lookup 真实检索人工判定表

用途：评估 `major_lookup` 面对真实用户专业文本时，是否能基于本地 MySQL 数据安全、准确、可解释地解析专业实体。这个表不是普通单测清单，而是人工评测工作台。

使用方式：

1. 每条 case 都连接本地 MySQL，真实调用 `major_lookup`。
2. 在“当前结果”里记录状态、选中的专业名称/代码、关键候选和 warning。
3. 在“人工判定”里填：`正确`、`未命中合理`、`召回不足`、`过度自信`、`应澄清`、`选错实体`、`需要产品决策`。
4. 已确认的问题再拆成回归测试、解析规则修复、别名 seed 修复或数据质量问题。

## 待产品确认的问题

- 在高考志愿咨询语境中，同名专业同时存在本科和专科目录时，`major_lookup` 是否应默认偏向本科？
- 多个候选都合理时，`major_lookup` 是否应该返回 `needs_clarification`，还是保持 `ok` 并只在候选列表里暴露歧义？
- `计算机类` 这类专业类词，应该在本工具里拒绝，还是转交一个支持专业类的 resolver？
- “专业”“中外合作办学”“师范”“五年制”等后缀归一，应该放在 `major_lookup` 内部、上游 NLU，还是独立 normalization 层？

## 本轮优先级结论

1. 最高优先级：修正同名本科/专科排序，至少在高考本科咨询语境下优先本科；涉及 ML016、ML017、ML029、ML030。
2. 高优先级：多候选/多义别名增加澄清机制；涉及 ML031、ML032、ML034、ML054。
3. 高优先级：拦截危险宽泛词误召回，尤其 ML035 “网络安全”。
4. 中优先级：增加后缀归一层；涉及 ML040、ML041、ML042、ML043。
5. 中低优先级：候选列表排序和展示降噪；涉及 ML002、ML003、ML006、ML007、ML008、ML010、ML026。
